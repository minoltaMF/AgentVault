# 持久正文索引性能基准

缓存查询重复采样、阶段诊断与 alpha.17 对照见[缓存查询尾延迟](search-index-tail-latency.md)。本页的三次缓存样本仅用于原有基准，不应据此推断尾延迟。

本基准使用临时合成会话，通过实际 CLI WebUI API 测量工作台扫描和正文搜索。它不读取或修改用户会话，不关闭其他进程。脚本保留临时夹具、服务器日志和文件哈希，便于检查结果。

## 复现

先按项目工具链构建 release CLI：

```sh
cargo build -p cc-session-manager --release --no-default-features --bin cc-sessions
node scripts/benchmark-workbench-index.mjs --cli /absolute/path/to/release/cc-sessions --sessions 1000 --messages 100 --body-length 1024 --output /absolute/path/to/result.json
```

Windows 使用 `cc-sessions.exe`。脚本只依赖 Node 内置模块；不安装浏览器或 Agent 运行环境。`--output` 指向结果文件，父目录须存在。快速检查可用 `--sessions 3 --messages 4 --body-length 128`。CLI 必须来自已确认的 release 构建；报告记录版本与二进制 SHA-256，路径中的 release 字样本身不是构建证明。

`--messages` 使用偶数，生成配对用户/助手消息。可用 `--providers workbuddy,grok` 只复测指定来源。用户正文关键词单独验证角色，所有命中均额外打开对应预览偏移；这部分预览校验时间不计入搜索耗时。

每个来源使用独立索引与进程，依次执行：扫描、首次索引、三次缓存查询、无命中查询、进程重启及历史列表加载、重启后查询、人工修改一份合成文件后查询，以及旧关键词消失检查。稀疏关键词只匹配一个会话，避免 100 条结果截断影响解释。每次查询都断言实际索引/复用数量、命中、无失败和无截断，修改前后分别校验所有原始夹具 SHA-256。脚本对文件的唯一主动修改是明确的单文件重建阶段。

## 测量边界

- 时间包含 HTTP 调用和 25 ms 轮询；很短的结果受到轮询精度影响。
- “首次索引”表示派生数据库为空，不代表操作系统磁盘缓存为空；不清空 OS 缓存。
- 正文是重复 ASCII 合成文本，不能代表自然语言、多语言、附件或真实分支复杂度。首次建索引、进程重启和单文件重建各测一次，缓存搜索保留三次原始值并取中位数，不推断 P95。
- 扫描与首次搜索分别计时；首次搜索仍可能为未缓存会话解析元数据。单文件更新查询仍检查整个显式范围，耗时不等于单文件解析耗时。
- 索引大小包含正文、投影事件和查询结构，是派生缓存而非备份。不把源数据字节数与索引字节数相等作为目标。
- 结果仅代表记录的机器、构建及文件系统；不作为所有平台的延迟保证，也不替代原生安装包或 UI 渲染性能验证。

## 2026-10-05 alpha.16 优化对照

本轮沿用每来源 1,000 会话 × 100 消息 × 1,024 正文字符的完整 CLI API 基准。机器与目标同上：Windows ARM64 虚拟机运行 x86_64-pc-windows-gnu release CLI，使用本地临时目录；每轮独立数据库，测量期间没有并行构建或测试。原始运行跨日，宿主负载与 OS 缓存未受控，因此数值表示这些具体样本，不表示固定加速比。

对照提交为 `995b7dcd40d4771a5750e1385b221d3e3e300e36`（alpha.15）。下表使用较晚的旧版复测；较早旧版、未包含删除扫描修复的中间候选及最终运行均保留在[脱敏原始结果](benchmarks/search-index-alpha16-20261005.json)，包括版本、二进制 SHA-256、时间戳与全部阶段。单位为秒。

| 来源 | 旧版首次 | 新版首次 | 首次耗时减少 | 旧版缓存中位数 | 新版缓存三次 | 新版缓存中位数 | 新版单文件更新 |
| --- | ---: | ---: | ---: | ---: | --- | ---: | ---: |
| qoder | 121.26 | 47.60 | 60.7% | 1.62 | 1.67 / 1.53 / 1.68 | 1.67 | 2.61 |
| workbuddy | 142.30 | 45.14 | 68.3% | 1.74 | 1.43 / 1.17 / 1.17 | 1.17 | 1.42 |
| grok | 136.28 | 35.11 | 74.2% | 3.75 | 2.61 / 2.33 / 2.48 | 2.48 | 2.80 |
| pi | 104.52 | 32.99 | 68.4% | 1.24 | 1.13 / 1.18 / 1.48 | 1.18 | 1.44 |

首次索引四来源均减少 60.7%–74.2%。缓存中位数在 WorkBuddy/Grok/Pi 上下降，Qoder 从 1.62 秒到 1.67 秒略升；Pi 的三次极差反而扩大，不能宣称波动已全面解决。这里只确认减少了重复读取和查询工作，缓存延迟及波动仍需更多样本评估。

实现包含三项优化：新文件跳过没有旧事件可删的 DELETE（旧查询计划为 `SCAN session_events`）；登记和投影合并为单文件事务并复用消息 INSERT；批量读取缓存摘要并按 Provider/路径查找，复用数据库连接及查询语句。已有文件的重建删除、文件指纹、路径与可见性校验、取消和失败回滚保持。未改变 schema 或 SQLite 同步设置。

仅合并事务与优化查询的中间候选并未稳定改善首次写入：Qoder/WorkBuddy 首次耗时分别为 185.15/166.74 秒，随后旧版复测为 121.26/142.30 秒。因此没有以该候选宣称首次写入提速；补充查询计划检查并修复新文件反复扫描事件表后重新运行。

最终四来源均通过：首次索引 1,000；重复与重启查询复用 1,000；控制修改一个文件后重建 1、复用 999，旧关键词消失；用户/助手命中角色及预览偏移正确，分阶段源文件哈希不变，无失败或截断。三次缓存查询不足以证明尾延迟稳定，仍存在宿主负载、文件校验和 Provider 元数据读取开销；首次索引和单文件更新各只有一次样本。索引仍保存正文与事件投影，本轮不解决派生数据体积，也不代表其他四个已索引来源的大样本性能验收。
