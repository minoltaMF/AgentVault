# Pi 来源校验与缓存尾延迟诊断

本专项沿用 alpha.17 的尾延迟问题，控制同一来源路径、同一派生索引与交替顺序。新增诊断，不修改搜索匹配、缓存失效、路径检查或原生会话。

## 可复现实验

候选程序为 alpha.18 的诊断代码，保留 alpha.17 的完整身份查询和外层去重。对照程序在独立检出上应用 [对照补丁](benchmarks/pi-tail-baseline-alpha18.patch)，仅恢复旧的两列身份查询及外层重复路径检查，模拟 alpha.16 的热查询路径。两者均使用完全相同的分段与资源采集代码；它们是实验构建，不把版本字符串当作发布二进制证明。结果必须保留两个可执行文件的 SHA-256。

```powershell
node scripts/benchmark-pi-tail.mjs --baseline C:/bench/baseline.exe --candidate C:/bench/candidate.exe --baseline-revision "alpha18 diagnostics + alpha16 lookup/outer check" --candidate-revision "alpha18 diagnostics + alpha17 optimizations" --output C:/bench/pi-tail.json
```

脚本只创建新的临时合成夹具：1,000 个 Pi 会话，每会话 100 条消息、正文 1,024 字符。先建立一次索引，随后 AB、BA 交替 30 轮，形成 ABBA 顺序；每次启动各查询先暖身，再测稀疏助手命中、无命中、用户命中。共 180 个正式样本及 180 个暖身样本，暖身不进入 P50/P95/max。每次重启不计入查询时间，命中预览校验也在计时之外。不同版本绝不并发搜索，构建和测试在测量前结束。

所有暖身和正式查询均断言零重建、全量缓存复用、无失败/跳过/截断，并校验用户/助手命中的预览 offset。实验前后逐文件 SHA-256 必须一致。所有慢样本保留；输出包含 UTC 起止时间、进程 ID、二进制身份、运行顺序和诊断原始值。脚本不删除夹具、不读取用户来源。

## 来源分段与资源指标

`AGENTVAULT_SEARCH_DIAGNOSTICS=1` 仍是唯一开关；未开启时不采集时钟或资源计数。

- `source_validation` 下细分 `path_boundary`、`source_id`、`open`、`file_metadata`、`fingerprint`、`adapter_registration`。
- Pi 注册再拆为 `pi_registration.validate`、`lock_wait`、`insert`，以区分路径验证与注册表锁等待。
- 这些是嵌套计时，父阶段已包含子阶段，不得重复求和。
- Windows 每次查询边界读取工作线程 user/kernel CPU 时间、原始 cycles、进程 I/O 次数与字节、系统 CPU busy 比例。API 失败、计数回退或身份不匹配返回 null；其他平台仍有阶段计时，resources 为 null。

[进程 I/O 计数](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-io_counters)涵盖进程所有线程，不能等同于物理磁盘读写。系统 CPU 的 kernel 计数包含 idle，计算 busy 时要扣除 idle，见 [GetSystemTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes)。线程 CPU 时间与 wall time 的差包括阻塞、调度、虚拟机停顿及采样误差，不能单独确定是哪一种等待。

Windows 旁路采样可在另一个终端运行：

```powershell
./scripts/sample-windows-search-system.ps1 -Output C:/bench/system.jsonl -StopFile C:/bench/stop.flag -DurationSeconds 1800
# 基准结束后创建停止标记，采样器将在下一轮退出。
New-Item -ItemType File C:/bench/stop.flag
```

它以约一秒间隔采集系统运行队列、上下文切换率与磁盘原始计数，保留采集起止时间，且拒绝覆盖已有输出。CIM 查询本身有开销；指标属于整个 Windows 客体，不能用于点名其他进程或证明单个线程等待原因。磁盘读取平均时间用相邻原始计数差除以基数差和 `Frequency_PerfTime`，无读取时报告 null。

本机尝试 WPR 的 CSwitch/ReadyThread/DiskIO 采集时返回 `0x80070005 Access is denied`，未提升权限，也未获得 ETW 线程级轨迹。系统队列和上下文切换率只能提供相关性，不能代替 ReadyThread 等待时间。原先 29 秒事件若未复现，不能事后确定其具体原因。

每版本每查询仅 30 个正式样本，P95 由极少尾部点决定，必须同时看逐轮配对差值。每个 visit 都重启并暖身，因此测量的是短生命周期进程中的热索引，不等同于桌面长时间运行。CIM 的调度与磁盘计数是顺序读取，采集周期包含查询开销，同一条记录也不是同步瞬时快照；对齐时必须保留其采集时间区间。

## 2026-10-08 实测结果

Windows 11 ARM64 虚拟机、6 个逻辑 CPU、约 9 GiB 内存，运行 x86_64 GNU release 程序。两份程序使用 Rust 1.90.0 和同版本 LLVM MinGW。原始样本、逐轮配对差值、资源指标和 254 条系统采样均保存在[脱敏结果](benchmarks/pi-search-tail-alpha18-20261008.json)。361 次查询（含首次索引、暖身）资源字段、PID 和核心阶段计数均核对完整；180 个正式查询均为 1,000 文件复用、零重建，来源前后哈希一致。

最初构建误用了共享 target 中的同一可执行文件，已在第 13 轮中止并记录 pass=false，不作为新旧对照。基线强制重建后，核对两份 SHA-256 不同，并用小夹具验证旧版每文件一次外层校验、新版无该阶段。脚本已增加相同二进制拒绝门禁，验证了拒绝时仍保存失败报告。下面仅统计纠正后的完整运行，没有剔除慢样本。

单位为毫秒。每行每版本 30 个正式样本：

| 查询 | 旧 P50 | 新 P50 | 旧 P95 | 新 P95 | 旧最大 | 新最大 | 配对差值中位数（新−旧） | 新版快于旧版 >25ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| sparse | 971.9 | 716.6 | 1198.8 | 1018.1 | 1643.4 | 1089.3 | -267.6 | 28/30 |
| absent | 814.6 | 589.8 | 956.6 | 751.3 | 1449.0 | 1473.4 | -225.9 | 29/30 |
| user | 949.9 | 674.5 | 1066.9 | 992.0 | 1116.9 | 992.8 | -254.7 | 28/30 |

本轮三类 P95 均下降，85/90 组配对快于旧版至少 25 ms；无命中新版最大值略高，不能说所有尾部都改善。这组受控交替结果不支持“新路径本身持续变慢”的判断，也不能替代长期多机测量。

### 已确认的耗时位置

候选程序来源校验中位数 389.8 ms，其中路径边界检查中位数 173.2 ms、Pi 注册中的再次验证 170.7 ms；逐样本计算的两次验证占来源校验比例中位数为 88.3%。注册锁等待每查询累计中位数 0.076 ms、最大 0.158 ms，不能将本轮卡顿归因于该锁。打开文件中位数 9.0 ms、读取文件元数据 4.3 ms、生成来源标识 28.7 ms。父子计时为嵌套关系，不能重复求和。

新旧来源校验总量接近（旧 384.5 ms，新 389.8 ms）；确认减少的是外层重复校验（旧中位数 172.7 ms）及身份/游标查询（97.2 → 21.2 ms）。工作线程 CPU 中位数由 859.4 → 625.0 ms，进程“其他 I/O 操作”中位数由 173,885 → 121,876；这些是系统调用/进程计数，不是同等数量的物理磁盘读取。

### 尾部样本并非同一种原因

1. 新版最大值：第 1 轮 absent，HTTP 1,473.4 ms，工作线程 531.4 ms，线程 CPU 531.3 ms，约 942 ms 位于工作线程计时之外。同一时段系统采样器上一次结束于 UTC 17:26:58.898，下一次开始于 17:27:00.809；扣除计划的一秒休眠，额外采样间隔约 911 ms（包含采样器写出等循环开销，不能直接视为精确调度等待）。独立进程的采样间隔也延长，支持共同调度/宿主停顿或计时观察链路的假设，不能归因为 Pi 解析或注册锁。包围该查询的客体磁盘读计数未增加，但不代表排除磁盘写入、宿主 I/O 或其他阻塞。
2. 新版第 9 轮 user：工作线程 964.6 ms、CPU 953.1 ms，来源校验 600.1 ms，其中两次路径验证 527.9 ms。这是以工作线程 CPU 消耗为主的慢样本，不能解释为纯磁盘等待。
3. 旧版第 13 轮 sparse：工作线程 1,577.7 ms、CPU 1,234.4 ms，FTS 763.0 ms；约 343 ms 未落在线程 CPU 时间里，来源校验为 441.2 ms。慢点也可能移到 FTS/其他等待，不能一律归为来源验证。

以上区分了程序固定开销、工作线程外延迟及线程内 CPU/等待混合，但没有获得 ETW ReadyThread 轨迹，无法进一步区分具体内核等待、客体抢占或宿主暂停；同一时段的关联不等于唯一因果。前轮 29 秒事件未复现，不能声称已找到该历史事件的根因或已修复。

## 下一步边界

优先设计并验证同一次查询内的路径验证复用：合并工作台和 Pi 注册中的重复边界遍历，同时保留 Pi 布局约束、打开前检查和最终指纹复核。不得跨查询信任旧验证结果，也不得以缓存索引授权缺失/越界文件。本轮只交付诊断与证据，不据此修改安全校验行为。若要确定历史长暂停的系统原因，需要能够采集 ETW 或宿主调度数据的环境，并捕获实际复现。
